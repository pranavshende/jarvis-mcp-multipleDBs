## 2. Invalidation & Security Isolation Verification

### 2.1. Composite Key Formulation
$$\text{CacheKey} = \text{SHA256}(\text{Query} \mid \text{Parameters} \mid \text{Role} \mid \text{AllowedScopes} \mid \text{UserId} \mid \text{ETLWatermark})$$

### 2.2. Verified Invalidation Policies
1. **Initial Cache Miss**: The first execution of an analytical or knowledge query always falls through to the active pipeline.
2. **Deterministic Financial Matching**: Varying a parameter (e.g. changing `target_date` from `2026-10-19` to `2026-10-20`) produces a verified cache miss. Fuzzy semantic matching is strictly disabled for financial metrics.
3. **Cross-Role Cache Isolation**:
   - `ROLE_SALES` querying cached data generated by `ROLE_WAREHOUSE` receives a cache miss.
   - `ROLE_WAREHOUSE` querying restricted AR metrics cached by `ROLE_FINANCE` receives a cache miss.
4. **User-Specific Isolation**: User A's private context is isolated by `UserId`; User B cannot retrieve User A's cached private results.
5. **ETL Watermark Invalidation**: Advancing the ETL watermark timestamp in `analytics.reconciliation_logs` invalidates prior financial cache entries immediately. Stale metrics cannot be served.
6. **Selective Invalidation Control Plane**: Administrative invalidation by scope (`ALL`, `FINANCIAL`, `KNOWLEDGE`, `ROLE`, `USER`, `WATERMARK`) clears targets accurately across L1 and L2 layers.
